## 1. THIS IS A REQUIRED GATE — NOT OPTIONAL READING

Before producing substantive implementation output, the AI builder MUST:

1. **READ** the required source set below.
2. **UNDERSTAND** the principles, authority, constraints, and quality expectations that apply to the task.
3. **OBEY** the applicable laws and protected requirements.
4. **ACT UPON** them in architecture, interface, interaction, implementation, verification, and delivery.
5. **PROVE** that the resulting work follows them.

Reading a document is not sufficient.

The builder must be able to translate the standards into actual decisions.

> **READ → UNDERSTAND → OBEY → APPLY → VERIFY**

This gate exists so the human does **not** have to paste or re-explain the same design/build intelligence before every app build.

---

## 2. THE UNIVERSAL BUILD PRINCIPLE

Naya Power does not begin each app from zero.

Every app inherits a default build DNA:

**CLARITY → SIMPLICITY → INTELLIGENCE → CRAFT → RESPONSIVENESS → ACCESSIBILITY → ROBUSTNESS → VERIFICATION → CONTINUITY**

The product's own mission determines **what** is being built.

Naya Power's operating standards determine the minimum quality of **how** it is built.

This means the AI should already know that:

- interfaces should be intentional rather than generic;
- primary actions should be obvious;
- controls need meaningful states;
- interaction should produce immediate, understandable response;
- visual design should communicate hierarchy and purpose;
- mobile is an intentional experience;
- accessibility is part of the build;
- performance matters;
- fake capability is prohibited;
- working systems are protected;
- implementation must be evidence-backed;
- completion requires verification;
- the AI must ask **WHY IS THIS NOT A 10?** before declaring the work complete.

The app-specific documents decide what is unique to that product. The universal standards establish the baseline.

# 5. THE DEFAULT ELITE INTERFACE LAW

Unless a product-specific authority explicitly requires a different treatment, Naya Power's default is:

> **MAKE DIGITAL OBJECTS FEEL PHYSICAL.**

And:

> **DEPTH → LIGHT → STATE → RESPONSE → CONSEQUENCE**

Therefore, a builder should never default to:

- generic browser buttons;
- dead rectangles;
- arbitrary cards;
- unexplained iconography;
- decorative motion without purpose;
- color without semantic meaning;
- interactions with no immediate feedback;
- desktop layouts merely squeezed onto mobile;
- fake capabilities;
- generic SaaS/dashboard patterns when the product calls for a richer experience.

This is a **default quality language**, not a mandate to make every app look identical.

The correct goal is:

**ONE QUALITY STANDARD — MANY PRODUCT EXPRESSIONS.**

Do not invent a conflict where none exists.

Do not override explicit product intent merely because the universal default is different.
