## 0. ACTIVATION PURPOSE

Activation 05 establishes the persistent application-level **Adaptive Learning and Compounding Intelligence layer** of Naya Power.

The underlying model is NOT assumed to rewrite its model weights because a conversation occurred. Naya Power therefore MUST implement learning as durable application state surrounding the model/runtime.

The purpose is not to create another memory system. The purpose is to make the existing intelligence architecture **learn from verified experience and use that learning to improve future behavior**.

The canonical transformation is:

```text
EXPERIENCE
→ OBSERVATION
→ LESSON
→ EVIDENCE
→ CONFIRMATION
→ RULE / PATTERN
→ PREFLIGHT
→ BETTER ACTION
→ NEW EXPERIENCE
```

The customer experience remains simple:

```text
ACTIVATE
→ CONNECT INTELLIGENT HUB
→ USE NAYA POWER
```

All implementation complexity MUST remain behind that experience.

## 1. NON-NEGOTIABLE LAWS

### LAW 01 — NO IMPORTANT MISTAKE REMAINS ONLY A MISTAKE

```text
MISTAKE → LESSON → RULE → PREFLIGHT
```

An apology is not learning.
A summary is not learning.
A stored note is not learning.
A proposed lesson is not an adopted rule.

Learning is complete only when the lesson is truthfully represented, appropriately evidenced, and—when justified—made available to future behavior.

### LAW 02 — ONE EVENT, ONE INTELLIGENCE OBJECT

```text
ONE HUMAN EVENT
→ ONE CANONICAL INTELLIGENCE EVENT
→ MANY USEFUL VIEWS
```

A Smart Note, Activity Intelligence Feed item, Learning Event, Intelligent Hub projection, daily learning entry, and related report MUST NOT become competing canonical copies of the same intelligence.

They are representations, relationships, projections, or lifecycle states around the canonical intelligence event.

### LAW 03 — NO SMART LINK, NO PROOF, NOT COMPLETE

A Smart Link MUST be treated as a durable relationship to evidence/provenance/related intelligence where the implementation supports that relationship.

A conversational claim such as `saved`, `learned`, `synced`, `adopted`, or `verified` MUST NOT substitute for evidence.

### LAW 04 — SOURCE INTENT IS NOT RUNTIME TRUTH

```text
DOCUMENTED
≠ IMPLEMENTED
≠ EXECUTED
≠ OBSERVED
≠ VERIFIED
```

No source file, commit, local test, CI success, deployment status, or generated artifact alone constitutes independent runtime proof.

Consequential release verification MUST follow:

```text
SOURCE
→ BUILD ARTIFACT
→ DEPLOYMENT
→ EXACT PUBLIC URL
→ INDEPENDENT RUNTIME OBSERVATION
```

### LAW 05 — LEARNED ≠ ADOPTED

A lesson MUST NOT silently become an operational rule.

```text
OBSERVED
→ PROPOSED
→ CONFIRMED
→ OPERATIONAL
→ SUPERSEDED
```

Evidence state and learning state MUST remain separate.

## 3. SMART NOTE CONTRACT — ACTIVATION 05 INTEGRATION

Activation 05 MUST consume the canonical Smart Note model established by Activation 01 and its binding amendment.

A Smart Note MUST represent one intelligence event and SHOULD preserve, when applicable:

1. `BIG TOPIC`
2. `DATE / TIME`
3. `TYPE`
4. `IN A NUTSHELL`
5. `HUMAN`
6. `NAYA`
7. `MACHINE`
8. `CHILD / GRANDMA`
9. `KEY POINTS`
10. `EVIDENCE`
11. `SMART LINK`
12. `LEARNING STATE`
13. `WHAT NAYA POWER LEARNED`
14. `ADOPTED`, when operational adoption is justified
15. `OPERATIONAL RULE / PREFLIGHT`, when one exists

The four perspectives are representations of the SAME event:

- **HUMAN:** what the human experienced, intended, decided, discovered, or considered meaningful.
- **NAYA:** what Naya understood, connected, inferred, or recommends. Inference MUST NOT be represented as a human-stated fact.
- **MACHINE:** structured representation supported by actual implementation, provenance, state, identifiers, and machine-relevant relationships.
- **CHILD / GRANDMA:** the simplest truthful explanation of what the intelligence means.

`IN A NUTSHELL` is the concise synthesis of the intelligence event.

`WHAT NAYA POWER LEARNED` is part of the SAME Intelligent Block. It MUST NOT create a second Smart Note.

## 8. LEARNING STATE MACHINE

The canonical learning lifecycle is:

```text
OBSERVED
  ↓
PROPOSED
  ↓
CONFIRMED
  ↓
OPERATIONAL
  ↓
SUPERSEDED
```

Rules:

1. `OBSERVED` means an event or possible lesson was observed.
2. `PROPOSED` means a candidate lesson/rule has been formulated but is not yet authoritative.
3. `CONFIRMED` means the lesson has adequate confirmation for the applicable governance boundary.
4. `OPERATIONAL` means the lesson is authorized for future behavioral use.
5. `SUPERSEDED` means a later, stronger, or governing intelligence state replaces it.

Contradictory intelligence MUST be represented rather than silently overwritten.

## 9. EVIDENCE STATE

Evidence MUST remain distinct from learning state.

Supported evidence progression includes:

```text
UNKNOWN
→ IMPLEMENTED
→ TESTED
→ VERIFIED
→ RUNTIME-PROVEN
→ PRODUCTION-PROVEN
```

A stronger evidence state MUST NOT be inferred merely from a weaker state.

Examples:

- GitHub file exists → implementation evidence, not runtime proof.
- Test passes → tested evidence, not production proof.
- Deployment succeeds → deployment evidence, not exact runtime observation.
- Exact public runtime independently observed → runtime proof.

## 10. ADOPTION / PROMOTION GATE

The system MUST NOT promote a lesson to `OPERATIONAL` solely because Naya generated it.

Operational promotion requires evidence appropriate to the lesson plus the applicable governance/authority boundary.

At minimum:

```text
CANDIDATE LESSON
→ EVIDENCE CHECK
→ GOVERNANCE CHECK
→ CONFIRMATION
→ OPERATIONAL PROMOTION
```

If evidence is insufficient:

```text
LESSON = PROPOSED
RULE = NOT OPERATIONAL
```

No self-certification is permitted.

A system MUST NOT use its own unverified assertion as the sole evidence that its assertion is true.

## 11. PREFLIGHT CONTRACT

Before consequential work, Naya SHOULD retrieve applicable operational lessons, rules, constraints, and regression guards.

Preflight MUST evaluate, where relevant:

- prior mistakes;
- verified lessons;
- known successful patterns;
- protected artifacts;
- immutable or locked requirements;
- user preferences;
- active constraints;
- release/runtime verification rules;
- required post-action observations;
- known regressions;
- superseded or contradictory rules.

A matching operational rule MAY warn, require additional verification, or block an unsafe action according to its authority.

Preflight MUST occur before consequential action whenever the connected runtime supports it.

## 12. REGRESSION GUARD

A verified mistake can become a reusable safeguard.

Canonical example:

```text
CANONICAL SOURCE = NAYAHUB.html

PROTECTED = existing architecture + functionality + navigation + intelligence structures + styling + JavaScript behavior

AUTHORIZED = explicitly requested surgical changes

FORBIDDEN = rebuild / replace / rename / delete existing foundation without explicit authorization

POST-ACTION = protected structures survive + requested change exists + required runtime verification is completed
```

Regression guards MUST be specific enough to prevent recurrence and MUST NOT become excuses for refusing authorized change.

## 17. IDEMPOTENCY / DUPLICATION CONTROL

Adaptive Learning MUST be idempotent wherever events are reprocessed.

Reprocessing the same canonical event MUST NOT create uncontrolled duplicate Smart Notes, duplicate Learning Events, duplicate rules, duplicate feed entries, or recursive self-generated event loops.

Identity SHOULD be based on stable event identifiers/fingerprints and canonical source relationships.

A stronger verified state MAY replace a weaker state, but repeated processing MUST preserve lineage and avoid unnecessary duplication.

## 18. FAILURE / PARTIAL SUCCESS CONTRACT

If any stage fails, Naya MUST report the actual state.

Examples:

```text

≠ PERSISTED
≠ FEED-PUBLISHED
≠ HUB-SYNCED
≠ LEARNED
≠ ADOPTED
≠ RUNTIME-VERIFIED
```

Partial success MUST be represented as partial success.

No downstream state may be claimed merely because an upstream state exists.

If verification fails, the system MUST NOT mark the corresponding learning or release as verified.
