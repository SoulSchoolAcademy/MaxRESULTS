# 05 — COPY CONTROL: ZERO IMPROVISATION DRIFT

Production copy has exactly three types.

## LOCKED

Text is supplied in this directive exactly.

The implementation AI MUST NOT rewrite it for style.

Examples:

`This isn't your judgment. It's your map.`
`NAYA · YOUR AI GUIDE`
`CHOOSE YOUR KEY`
`ZERO COST TO START`

## DATA-FILLED

Sentence structure is fixed; variables are inserted from authoritative data.

Example:

`[NAME], I've looked at your results.`

`Your strongest signal is [STRONGEST_DIMENSION].`

`Your current MAXESS stage is [STAGE].`

The AI may not alter the sentence structure unless explicitly instructed.

## GENERATED-BY-NAYA

Naya may generate interpretation only within the contract defined below.

Naya-generated interpretation MUST be:

- conversational;
- warm;
- intelligent;
- direct;
- specific;
- useful;
- non-salesy;
- non-judgmental;
- concise;
- grounded in supplied result data.

Maximum lengths:

Hero interpretation: 45 words.
Score meaning: 90 words.
Dimension interpretation: 60 words.
Pattern interpretation: 90 words.
Strength interpretation: 80 words.
Naya Masters relevance: 45 words per Master.
Final invitation: 65 words.

Purpose:
translate measurement into practical understanding.

Required inputs:

- authoritative `window.MAXESS_RESULT`;
- overall score;
- mastery stage;
- five dimension scores;
- strongest dimension;
- lowest/relevant opportunity dimension when appropriate;
- available goal/profile context;
- approved MAXESS language.

Required output structure:

1. WHAT I NOTICE
2. WHY IT MATTERS
3. WHAT YOU CAN DO

For very short surfaces, compress to:

NOTICE → MEANING → NEXT.

Prohibited claims:

- guaranteed outcomes;
- guaranteed income;
- medical claims;
- psychological diagnoses;
- invented personal facts;
- invented achievements;
- invented score data;
- invented pathway relevance;
- fear-based pressure;
- false scarcity;
- unsupported “scientific” certainty.

NO FILLER COPY RULE:

If a sentence does not help the user understand, feel, trust, remember, or act, delete it.

Never write copy merely to fill empty space.

Never invent a sentence simply because a section “needs more text.”

# 15 — COMPONENT / EDIT OWNERSHIP BOUNDARY

Every visible component has exactly one active owner.

A micro-edit MUST identify:

REQUEST
→ COMPONENT
→ OWNER
→ SOURCE REGION
→ PROPERTY
→ OLD VALUE
→ NEW VALUE
→ VALIDATOR

Example:

“Make Orb 10% smaller.”

Owner: Signature Orb
Property: desktop diameter token
Source region: Orb component only
Allowed change: size tokens + dependent ring sizing
Forbidden changes: Naya copy, report, Masters, data contract.

Micro-edits may not rewrite or reorder unrelated sections.

A section edit may change multiple owned components inside that section, but may not modify another section's owner without explicit dependency justification.

A release edit must explicitly declare cross-section effects.

---

# 16 — FAST EDITABILITY CONTRACT

The product must be maintainable at the pace of normal design iteration.

Target cycle for a micro-edit:
LOCATE
→ PATCH
→ TARGET-LANGUAGE VALIDATE
→ LOCAL QA
→ CHECKPOINT

Target: 1–5 minutes where the requested change is genuinely local.

No full release QA for a color/spacing/typography micro-edit unless risk analysis identifies a genuine release-level dependency.
No whole-page rewrites for local changes.
No stash as the normal storage for verified product mutations.
Verified mutation must become:
COMMIT
→ PUSH
before continuing.

# 17 — EVIDENCE STANDARD

A design claim is not evidence.
A QA PASS is not evidence of visual excellence.

Evidence may include:
- source diff;
- rendered artifact;
- browser inspection;
- responsive inspection;
- screenshot/comparison;
- interaction verification;
- accessibility verification;
- PDF inspection;
- actual data validation;
- commit SHA.

Freeze a unit only when its critical acceptance criteria have evidence.
Target: 9.5+.
No major category below 9.
