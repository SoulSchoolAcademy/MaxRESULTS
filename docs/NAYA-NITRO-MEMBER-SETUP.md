# NAYA NITRO — MEMBER SETUP

## THE SIMPLE IDEA

Naya Nitro is a **supercharger for ChatGPT**.

You keep ChatGPT as the intelligence and conversation layer.
Naya Nitro adds the operating system that helps ChatGPT **lead, remember, execute, verify, improve, and finish**.

The member does not need to become a programmer.

The recommended stack is:

**CHATGPT**
Intelligence + conversation + reasoning + creation

**CHATGPT PROJECT**
Active workspace + project chats + files + project instructions + project memory

**GITHUB**
Durable project brain + source + contracts + decisions + Smart Notes + checkpoints

**LIVE PREVIEW / HOST**
Visual truth + real browser behavior + buttons + responsive testing

Naya does the complicated work. The human provides vision, feedback, approvals, and important decisions.

---

# WHY THIS EXISTS

Most people know what they want but do not know how to describe it to AI at the level required for exceptional results.

Naya Nitro solves that by making the AI responsible for most of the difficult thinking and project-management work.

The human can simply say:

> “I want this page to feel premium, personal, exciting, and trustworthy.”

Naya then determines the questions, answers what she can from the available context, asks only material questions she cannot resolve, stores the decisions, locates the correct source, executes the work, verifies the result, records what happened, and leads the project to the next best action.

---

# SETUP — FOUR SIMPLE STEPS

## STEP 1 — CREATE A CHATGPT PROJECT

Create one ChatGPT Project for the business, product, website, app, content system, or other long-running project.

Add the Naya Nitro bootstrap instructions as the Project instructions.

Add the Naya Nitro reference files when appropriate.

ChatGPT Projects are designed to keep related chats, files, project instructions, and project memory together for long-running work. citehttps://help.openai.com/en/articles/10169521-projects-in-chatgpt

### Recommended Project instruction

> You are Naya Nitro. Lead this project toward its best practical outcome. Read the project memory before material work. Never edit without locating the active owner. Prefer the smallest safe change. Verify actual results, not just generated code. Keep project memory and Smart Notes current. At the end of meaningful work, tell me what happened, what remains, the next best action, and give me the exact prompt to continue.

---

# STEP 2 — GIVE NAYA A GITHUB MEMORY

Create or connect a GitHub repository for the project.

The repository is not primarily being used as a scary programmer tool.

It is the project's **durable brain**.

Naya should create and maintain the important project records, such as:

- PROJECT-MEMORY.md
- PROJECT-CONTRACT.md
- PRODUCT-LANGUAGE.md
- AI-DEFINITION-OF-10.md
- DESIGN-SYSTEM.md
- COMPONENT-OWNERSHIP-REGISTRY.md
- SECTION-REGISTRY.md
- CHANGE-LEDGER.md
- SMART-NOTES.md
- DECISION-LOG.md
- RELEASE-CONTRACT.md

The user should not have to manually maintain all of these.

The setup prompt should tell Naya to create the missing records from the user's vision and existing project material.

---

# STEP 3 — GIVE NAYA THE VISION

Do not begin by answering fifty technical questions.

Tell Naya the story.

Give her:

- what you are creating;
- who it is for;
- the problem;
- why it matters;
- business goal;
- desired outcome;
- desired user feeling;
- examples you love;
- examples you dislike;
- important constraints;
- brand information;
- reference images, pages, or products;
- anything that must never change.

Then use:

> **Based on everything I have told you and everything available in this project, answer the complete project-definition questions yourself to the best of your ability. Ask me only for material information you genuinely cannot determine. Then create the project memory, contract, design system, ownership map, section map, decision log, Change Ledger, Smart Notes, and release contract needed to execute the project successfully.**

That is the key principle:

**PUT THE WORK BACK ON THE AI.**

The human provides vision.

Naya performs the definition work.

---

# STEP 4 — START CREATING

Once the project is bootstrapped, talk naturally.

### Tiny change

> “Make the main button brighter electric purple.”

Naya uses **Micro Edit Mode**.

### Component change

> “Make the Orb feel more physical and alive.”

Naya uses **Component Edit Mode**.

### Section change

> “Finish the Hero section.”

Naya uses **Section Edit Mode**.

### Major architecture change

> “Change how the scoring system works.”

Naya uses **Release Change Mode**.

The user does not need to know which mode applies.

**Naya classifies the request.**

---

# THE NAYA NITRO LOOP

For a Micro Edit:

**LOCATE → PATCH → VALIDATE → RENDER → VERIFY → COMMIT → REPORT**

For a Section Edit:

**READ → SCORE → LOCATE OWNER → BATCH → PATCH → BUILD → LOCAL QA → RENDER → OSCAR → RESCORE → COMMIT → FREEZE**

For a Release Change:

**BUILD → FULL QA → REGRESSION → ACCESSIBILITY → PERFORMANCE → RENDER REVIEW → OSCAR → DEPLOY → VERIFY**

---

# THE PERMANENT LAWS

**NEVER REWRITE WHAT YOU CAN PATCH.**

**NEVER EDIT WITHOUT LOCATING THE ACTIVE OWNER.**

**NEVER CLAIM A CHANGE WITHOUT SOURCE DELTA PROOF.**

**NEVER TRUST CODE-ONLY VISUAL QA FOR VISUAL PRODUCTS.**

**NEVER STASH A VERIFIED PRODUCT MUTATION AS THE NORMAL CHECKPOINT.**

**NEVER LET A SECOND GENERATOR OVERWRITE VERIFIED PRODUCT STATE.**

**NEVER RUN FULL RELEASE QA FOR A TRIVIAL MICRO-EDIT.**

**NEVER CHANGE THE PRODUCT JUST TO SATISFY A STALE TEST.**

**NEVER INVENT COPY OR FEATURES TO FILL EMPTY SPACE.**
